# TACT Borrowed Patterns

Source: [Tier S Prior Art Blitz](../prior-art/tier-s-summary.md) (Preloop, BoundFlow, HumanLayer Agent Control Plane, AXME; "chowki" could not be identified — see [chowki.md](../prior-art/chowki.md)), corrected 2026-09-08 against TACT's actual existing code (`core/tact-work/types.ts`, `supabase/migrations/20260905000000_create_tact_work_tables.sql`).

This document is the durable record of *which* external patterns TACT has decided to borrow, adapt, reference, or reject, and *why* — so future Phases don't have to re-derive this reasoning or re-read all 5 individual Prior Art files. It does not authorize implementation; each row's "Implementation Phase" is a proposal, not a start signal.

## Principles

TACT observes the following when evaluating and using Prior Art. These are restatements of existing TACT Canonical Model rules, not new rules — Prior Art review does not get to loosen them:

- **TACT's center is Work, not Agent.** Agent/LLM/SaaS/Human are Participants/Capabilities that help complete Work — never the organizing concept.
- **Conversation ≠ Work.** They remain distinct entities; `Work.id` must never equal `Conversation.id`.
- **Run = one execution attempt.** A retry is a new Run, never a mutation of an existing one. This is settled — see Correction 1 in `tier-s-summary.md`.
- **LLM ≠ Authorization layer.** Policy/Permission/Approval decisions are enforced deterministically at the Execution Layer, never by LLM judgment, and never by a prompt.
- **Context read permission ≠ Action write permission.** These are separate permission types, evaluated separately.
- **Provider neutrality is non-negotiable.** No vendor/provider-specific ID or shape leaks into TACT's canonical domain types.
- **Supabase is the single source of truth** for TACT-owned state. Any borrowed schema is re-expressed as Supabase tables/RLS, never imported as a second store.
- **A protected side effect never executes before its Approval is granted**, and an already-successful side effect is never casually re-executed.
- **Borrow pattern, not accidental architecture.** A Prior Art project's entity model, scope, or agent-centric framing is not adopted just because its narrower pattern is useful.
- **License-first.** Nothing is classified REUSE without a directly verified license; cross-language/cross-runtime code is REFERENCE_ONLY or REJECT for practical reuse regardless of license permissiveness.
- **Build less. Orchestrate more.** Borrow first, internalize later — but "borrow" here has meant *patterns and schema shapes*, not runtimes, in every case found so far (see External Execution Engine row).

## TACT-specific decisions (this integration pass)

1. **Work / Task / Run** — **KEEP**, with `Run = one execution attempt` explicitly reconfirmed as non-negotiable (already implemented via `Run.attempt`, Phase B1).
2. **PolicyDecision** — **ADD candidate**: `ALLOW / REQUIRE_APPROVAL / REQUIRE_INPUT / DENY`. Exact name/type left to ARCH-P2; not designed here.
3. **Approval payload binding** — **HIGH PRIORITY ADD candidate**. At Approval time, the approved Action/Payload and, at execution time, the about-to-execute Action/Payload must be deterministically confirmed identical. Candidates to evaluate in ARCH-P1 (not decided here): canonical payload, canonical serialization, payload hash, action identity, approval version, policy version. No implementation in this pass.
4. **Anti-self-approval** — **ADOPT PATTERN**. Design a protocol boundary such that an LLM/Agent/Tool is never treated as the answering party for a Human approval/input it is itself waiting on.
5. **HumanInteraction** — **ADD candidate**, does not replace Approval immediately. Future extension target: Approval / Clarification / Selection / Review / Assignment / Confirmation / ManualAction, as a shared upper concept.
6. **Waiting reason** — **ADOPT PATTERN candidate**, gated on compatibility with the existing `WorkStatus` enum (which already has two specific waiting states baked in). Decide in ARCH-P3, not here.
7. **Audit** — dedicated append-only Audit/Event entity, **ADD candidate**. Direction: track who requested what, what was referenced, what was decided, what was executed, which credential was used, what returned, and how state changed — not just Run metadata.
8. **Retry** — TACT canonical: **retry = new Run**. Same-Run mutation is not adopted. (Already implemented.)
9. **Claim / Lease** — **ADD candidate**, as the primitive separating HTTP request lifetime from Work execution lifetime.
10. **External Execution Engine** — **DEFER**. Not decided by this Tier S round alone.

## Priority Architecture Phases (proposed, not authorized)

Candidate order re-evaluated against the actual repo state (`core/tact-work/*`, Phase B1 migration) rather than accepted as originally proposed:

**ARCH-P1 — Approval Integrity** *(no dependency on the others; can start first)*
Payload binding, canonical action identity, mutation detection, stale-approval invalidation, execution-boundary enforcement. This is the highest-priority item in the whole matrix because `Approval` already exists and is already live in production (`core/tact-work/execution.ts` → the Slack Bot's `executeApprovedIntegrationAction()` flow established earlier this session) with no such protection today — it is an additive, backward-compatible schema change to an existing entity, not new architecture. Full design: [approval-integrity.md](./approval-integrity.md) (recommends a versioned, stored+hashed `ApprovalSubject`, split into P1a/schema → P1b/capture → P1c/verification).

**ARCH-P2 — Policy Decision Model**
`ALLOW / REQUIRE_APPROVAL / REQUIRE_INPUT / DENY`, fail-closed, static Permission vs dynamic Policy split. Does not block ARCH-P1 (Approval already exists independent of how the decision to require one gets formalized) but should land before ARCH-P3, because ARCH-P3's Clarification/HumanInteraction design needs a formal `REQUIRE_INPUT` outcome to hang off of — today that path is informal.

**ARCH-P3 — Human Interaction Model**
Approval as one kind of a broader concept; Clarification; correlation/resume token; pause/resume; anti-self-approval boundary; the `waiting_reason` vs. explicit-waiting-states decision. Depends on ARCH-P2's `REQUIRE_INPUT` vocabulary existing first.

**ARCH-P4 — Audit Event Model**
Append-only execution evidence: actor, Work/Task/Run, capability/provider, credential-owner reference (if one exists by then), policy decision, external effect, cost, state transition. Benefits from ARCH-P1–P3 being stable first, so the event schema captures the right fields on the first attempt rather than needing early revision — but is not strictly blocked by them. This directly fulfills the deferred `Event` entity named in TACT's own Phase B1 migration comment.

**ARCH-P5 — Durable Execution Foundation**
Claim, lease, worker ownership, resume, crash recovery, HTTP-lifecycle separation. Correctly last: it needs Run semantics already settled (they are — retry = new Run, already implemented) and needs the pause/resume vocabulary from ARCH-P3 to know what it's persisting through a crash. This is also the largest architectural lift in the matrix (claim/lease + a scheduled sweeper + an infra decision for where that sweeper runs) and should not be started before the smaller, more self-contained phases above land.

No implementation of any ARCH-P phase is authorized by this document. Each requires its own explicit Phase instruction per CLAUDE.md §13.
