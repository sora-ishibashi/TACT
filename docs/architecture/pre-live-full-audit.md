# TACT Pre-Live Full Repository Audit

Status: audit only. No production code, migration, dependency, config, or environment was changed to produce this document. Git checkpoint: HEAD `f580b6b` (`docs: define tact runs boundary`), branch `main`, already pushed to `origin/main` before this audit began. Findings are grounded in files actually read this session (directly, or via five parallel read-only sub-agents whose reports are merged below) — every claim below traces to a file:line citation. Where something could not be verified, it is marked **[UNVERIFIED]** rather than assumed.

This audit is not written to reassure. It is written to find what would break in production. Severity is never softened for "student project"/"MVP" reasons, and theoretical risk is explicitly distinguished from confirmed current production risk throughout.

---

## 1. Executive Summary

TACT's canonical Work/Task/Run/Policy/Approval/Clarification/Audit/RuntimeAdapter/Resume architecture (P2–P6b, ARCH-RUNS-1) is **substantially sound** — ownership, correlation, and Approval Integrity checks are consistently applied, dependency direction is clean, and this session's own concurrency tests demonstrate a genuine exactly-one-canonical-Run-claim guarantee. That architecture is not where this audit's worst findings are.

**The worst findings are in code adjacent to, but outside, that canonical architecture — specifically two live, unauthenticated production API routes:**

- **`app/api/tact/code-tasks/run/route.ts`** (and its sibling `approve`/`execute`/`commit`/`push`/`pull-request` routes) has **zero authentication of any kind** and, when reached, drives a real autonomous coding-agent execution (file writes, `git commit`, `git push`, GitHub PR creation via the `gh` CLI) against the live server checkout, using free-text instruction supplied directly by the caller. This is wired into the shipped UI shell (`components/tact/CodeSection.tsx`). **This is the single most severe finding of this audit.**
- **`app/api/tact/route.ts`** (POST) and **`app/api/tact/stream/route.ts`** (GET) have no authentication and invoke the Legacy 9-Agent workflow engine (`core/workflow`), which this repository's own documentation and this session's own earlier architecture work repeatedly assumed was "frozen and unreferenced." **It is not unreferenced — it is a live, reachable route.** These write into 8 tables (`conversations`, `conversation_messages`, `conversation_workflow_runs`, `tact_execution_history`, `tact_memory`, `tact_core_knowledge`, `tact_core_memories`, `tact_core_examples`) that carry `using(true)` Row Level Security policies — meaning any holder of the public anon key (which is, by Supabase's own design, embedded in every client bundle as `NEXT_PUBLIC_SUPABASE_ANON_KEY`) can read, write, or delete every row in these tables directly via the Supabase REST API, bypassing the app entirely.
- **No mechanism in this repository verifies that production's database schema actually matches `supabase/migrations/`.** This exact gap has already caused a real incident (missing `tact_clarifications`, `tact_audit_events`, `allowed_approver_ids` in production, discovered during this session's own earlier Live Acceptance work) and remains fully open today.

Alongside these, real (but lower-severity) correctness gaps exist in the canonical architecture itself: non-transactional multi-step state transitions in `core/tact-work/` can strand a Task in `"running"` with no Run (or a completed Run with a stuck Task) on a mid-write crash/timeout, and no reconciliation sweep covers this case (only the Runtime-dispatch-specific ambiguous-start case does). A third, independent Task/Run-shaped model exists in `core/tact-agent/` (coding-agent orchestration) that fully bypasses the canonical `tact-work` Work/Task/Run model. The primary Web Research path has no cap on decomposed sub-query count, making it a real, unauthenticated-reachable cost/DoS surface.

None of this diminishes what P2–P6b actually built: the Policy/Approval/Resume/Reconciliation core is well-designed, well-tested (relative to the rest of the repo), and internally consistent. The problem is that this audit's job was to look past that core, and immediately outside it are two live P0s that must be closed before any real-world SaaS integration work (Gmail/Notion/Drive/Calendar) begins — those integrations would multiply the blast radius of an already-open remote-code-execution and unauthenticated-data-exposure surface, not just add new capability.

## 4. Work/Task/Run findings (Phase 3)

**New finding this session, not previously documented: a real "stranded Task" window exists.**

`prepareRunForExecution()` (`core/tact-integration/execution.ts`) performs two non-transactional Supabase writes in sequence:

```
await deps.updateTaskStatus(workId, userId, accessToken, taskId, "running");  // write 1
const run = await deps.createRun(workId, userId, accessToken, taskId, {...}); // write 2
```

If the process crashes, times out (serverless function limit), or `createRun()` throws (including the legitimate concurrent-claim race this session's own P6b work relies on) **between these two writes**, the Task is left at `"running"` with **zero** Run rows. Because the *only* gate that allows a new attempt to start is `task.status === "pending"` (`prepareRunForExecution()`'s own precondition, and `evaluateTaskResumeEligibility()`'s `task_already_running` block, added this session), **this Task can never be resumed or retried again through any existing code path** — it is permanently stuck, and nothing detects or repairs it. The symmetric case exists on completion: `executeIntegrationActionCore()` calls `completeRun()`/`failRun()` *before* `updateTaskStatus(...,"completed"/"failed")`; a crash between them leaves a **completed or failed Run with a Task still reporting `"running"`**. Only the Runtime-dispatch-specific *ambiguous-start* case (P5d) has a reconciliation mechanism (`reconcileRuntimeExecution()`) — there is no general "does Task.status match the terminal state of its most recent Run?" sweep anywhere in the codebase.

This session's own `evaluateTaskResumeEligibility()` (P6a) correctly **fails closed** on this state (`task_already_running` blocks resume) — it does not make the problem worse — but it also provides no path to recovery. Today this requires manual DB intervention.

**Severity: P1.** This is a real, non-hypothetical gap in the canonical execution boundary (not the Legacy/code-tasks periphery), matches the audit's own named example ("Task runningなのにRun無し") exactly, and would become more consequential as multi-SaaS Work volume increases (Section 21).

Other checks: no evidence of "completed Run + pending Task" or "multiple simultaneously-active Runs for one Task" in the *canonical* path — the `idx_tact_runs_task_id_attempt` unique index and the P6b concurrency tests rule this out for concurrent-request races specifically. `WorkTask.status`'s dual role (business vs. execution-phase signal) is reconfirmed from ARCH-RUNS-1, not newly discovered, and remains a documented tension rather than a fixed schema issue.

## 5. Concurrency/idempotency findings (Phase 4)

| Path | Mechanism | Classification |
|---|---|---|
| New Run creation (any caller) | `idx_tact_runs_task_id_attempt` unique index (DB-level, atomic) | **Exactly-one canonical Run claim** — verified by this session's own `Promise.all` concurrency tests (`tests/tact/conversation/taskResumeExecution.test.ts`) |
| Slack webhook duplicate delivery | `tact_bot_processed_events`, unique index `(channel, external_event_id)`, atomic insert-or-23505 | **At-most-once claim, atomic** — confirmed by dedicated sub-agent trace, not a check-then-insert race |
| Trigger.dev dispatch retry/ambiguity | Trigger.dev's own `idempotencyKey` (server-side, official primitive) + `reconcileRuntimeExecution()`'s point-lookup recovery | **At-most-once dispatch, best-effort recovery** — explicitly does not claim Provider-level exactly-once (correctly hedged in this session's own P5d/P6b comments) |
| Approval double-click / Clarification double-answer | Non-atomic `status !== "pending"` check-then-write | **Harmless in practice**: worst case is a redundant idempotent write of the same status; the actual side-effect-producing step (Run creation) is still protected by the unique index above, independent of this race |
| Reconciliation concurrent invocation | Idempotency-key point lookup (Trigger.dev's own guarantee) | Already tested (`reconciliation.test.ts`) |
| `tact_conversation_message_attachments` link creation | PRIMARY KEY `(message_id, attachment_id)` + UNIQUE `(message_id, position)` | Atomic, DB-enforced |
| **`app/api/tact/code-tasks/*` family** | **None** — no auth, no rate limit, no idempotency guard beyond a status-string check anyone can set themselves | Not a race-condition problem — it's an authorization problem (Section 15) |

No instance of an unqualified "exactly-once" claim (in the Provider-delivery sense) was found anywhere in `core/**` — this session's own P5d/P6b comments and the `p2-p5-final-architecture.md` doc consistently scope the word to "the provider is called exactly once *per attempt*, with no automatic retry loop," which is an accurate, verifiable claim (`core/tact-integration/execution.ts`'s single, unguarded call to `deps.executeIntegrationAction(...)`), not an overclaim about network delivery.

**Test coverage gap**: across all 157 test files, exactly **one** file (`tests/tact/conversation/taskResumeExecution.test.ts`, added this session) uses `Promise.all` to exercise a genuine concurrent-invocation scenario. Every other "duplicate protection" claim in the codebase (Approval double-click, Slack dedup, reconciliation) is verified only by *sequential* test calls, not actual concurrent ones, even though the Slack dedup and Run-claim mechanisms are DB-index-backed and would very likely hold under real concurrency — this is a testing-thoroughness gap, not a code defect, but is worth naming (Section 18).

## 6. Approval / Human Interaction findings (Phase 5)

- **`rejectApproval` multi-task asymmetry (known debt) — confirmed still present, source-level**: `core/tact-work/approval.ts:469-471`, unchanged comment: rejecting one Approval does not cancel other pending Approvals on the same Work. The Work itself correctly moves to `"failed"` (terminal-Work guard prevents any of the orphaned Approvals from later resuming it — `work_not_resumable` fires safely), so this is an *orphaned-row hygiene* issue, not a security or double-execution issue. **Severity: P2** (unchanged from the code's own self-assessment; no escalation found).
- **Anti-self-approval / allowed-approver checks**: present and correctly ordered before any state mutation (`checkApproverAllowed()`, called before `updateApprovalStatus()` in both `approveApproval()`/`rejectApproval()`). No live producer sets `requestedByActorKind === "user"` today, so this defense is currently dormant-but-correct (P3/DEFER, matches the code's own documented reasoning).
- **Approval Integrity**: full re-verification (`verifyApprovalIntegrity()`) on every execution attempt, dedup-before-integrity ordering confirmed correct (a successfully-executed Approval is never re-flagged as a mismatch). No regression found.
- **Action/connection/policy mutation after Approval**: `executeApprovedIntegrationAction()`'s live Policy recheck (step 5.5) + Approval Integrity subject-hash comparison together catch both "the action definition changed" and "the risk class changed" between Approval-time and execution-time. `policyVersion` remains unpopulated (reserved field) — see Section 7.
- **Execution after reject**: structurally impossible — `rejectApproval()` never reaches any execution boundary (verified this session in the P6b refactor's own test suite, Case4).
- **Clarification**: `resolveClarification()` mirrors Approval's discipline (allowed-responder check, Work-state guard, no execution call). No multi-simultaneous-Clarification-specific bug found beyond the same "no auto-cancel of siblings" pattern as Approval (same P2 classification, not separately worse).
- **`expiresAt` fields (Approval and Clarification) are declared but never enforced** — no sweep/cron ever transitions a stale `pending` row to `"expired"` (consistent with this repo's own repeated "cron/scheduler禁止" convention across many phases). A months-old pending Approval remains approvable indefinitely. **Severity: P2** (operability, not security — the approver would still need legitimate access to approve it).

## 7. Policy findings (Phase 6)

`PolicyDecisionOutcome` (`allow|require_approval|require_input|deny`) is exhaustively switched everywhere it's consumed (`core/tact-integration/execution.ts`, `core/tact-conversation/orchestration.ts`'s P6b addition) — confirmed via the `const exhaustiveCheck: never = ...` pattern present at every switch site checked this session. Policy is re-evaluated at every point the brief asks about: before execution (`executeApprovedIntegrationAction()` step 5.5), before resume (`executePreparedTaskResume()`, P6b, this session), and read actions re-evaluate it independently of the write path. Runtime/Provider code has no visibility into `PolicyDecision` at all — it cannot override it (`RuntimeAdapter`'s contract carries no Policy field). `riskClass` and `PolicyDecisionOutcome` remain genuinely separate axes (`PolicyDecision.riskClass` is an independent field), no conflation found. `policyVersion` remains an unpopulated reserved field; given `POLICY_ALLOWLIST` is a static in-code data structure with no runtime-mutable admin surface today, the practical risk of its absence is low (**P3/DEFER**) — it would need escalation only if a runtime-configurable Policy admin panel is ever built.

## 8. Runtime/reconciliation findings (Phase 7)

The P5d-era failure mode (ambiguous Trigger.dev start → `reconcileRuntimeExecution()` recovery → Run completed) is **structurally general**, not a hardcoded fluke: it is driven entirely by `RuntimeError.outcomeKnown` (a boolean derived from exception *type*, not from any Run/Task-specific state) and the shared `(task_id, attempt)`-keyed idempotency scheme, both reusable for any future `RuntimeAdapter` implementation. `Trigger start success + externalRef attach failure` is an explicitly acknowledged, narrow known-debt (`execution.ts`'s own comment, "P5d reconciliation debt") — low risk because it's a read-only slice today. Local-dev-vs-production Trigger.dev environment-key confusion (the exact failure this session diagnosed live during P5d Live Acceptance) has no structural guard beyond this session's own added CLI preflight (`getMissingRequiredEnv()`) — that preflight catches *missing* env vars, not a *wrong-environment* key (a syntactically valid key for the wrong Trigger.dev environment). **Severity: P2** — a real operational footgun (already occurred once), partially but not fully mitigated by this session's own P5e hardening.

## 9. Integration Gateway findings (Phase 8)

Connection ownership, service/operation allowlisting, read/write distinction, and raw-provider-error containment (`IntegrationErrorCode` taxonomy) are all correctly enforced at `core/tact-integration/execution.ts`'s boundary — confirmed via this session's own extensive prior reading (P5c–P6b) and re-confirmed here with no new contradiction. Policy decisioning is not duplicated or second-guessed by the Integration layer (`gateway.ts`/`providers/composio/**` never import `policy.ts`, confirmed via grep). **The three-boundary mixing inside `execution.ts` (Policy/Integrity=Core, Run lifecycle=Runs, dispatch=Integration) is a known, already-documented ARCH-RUNS-1 violation** (Section 20) — re-confirmed present, not newly discovered, correctly triaged as DEFER (it is the load-bearing, production-proven boundary; splitting it now is out of scope for an audit).

## 10. Slack trusted boundary findings (Phase 9)

Full end-to-end trace performed by dedicated sub-agent. **Result: sound, no exploitable gap found.** Signature validation is Slack's official HMAC-SHA256 scheme, on the raw body, before `JSON.parse`, fails **closed** if the signing secret is unset (401), and uses `crypto.timingSafeEqual`. A 300-second replay window is enforced independently of the signature check. Event dedup is a genuine DB-unique-index atomic claim, not check-then-insert. Identity resolution never trusts a raw Slack user id directly and is correctly scoped by `(provider, external_user_id, external_workspace_id)`; a previously-real historical bug in this area (S1e, missing `organizationId` forwarding on one entrypoint) has already been fixed. Bot-echo/loop protection is present and generic (Slack's own `bot_id`/`subtype` markers, not a self-ID special case). Outbound Slack send failures are isolated from canonical Work/Task/Run/Approval state — a failed reply never leaves the underlying state machine stuck. There is **no** Slack interactive Block Kit (`block_actions`) handler at all today — approval decisions are plain-text replies, correlated purely via server-side thread lookup, going through the exact same signature/dedup pipeline as any other message. **Forward-looking note (not a current gap): if Block Kit buttons are ever added, that new payload type would need the identical signature-verification treatment — flag as P2 for whoever implements it, not before.**

## 11. Database/RLS findings (Phase 10)

Full migration-by-migration read by dedicated sub-agent (all 21 files). Ownership enforcement (`auth.uid() = user_id` direct, or EXISTS-through-parent) is consistent and correct across every canonical (`tact_*`) table. Service-role-only tables (`tact_external_identities`, `tact_bot_conversation_links`, `tact_bot_processed_events`) genuinely have zero RLS policies (correct deny-all-without-service-role behavior), matching `core/database/supabaseServiceRole.ts`'s documented allowlist. FK cascade philosophy (`work_id` always CASCADE, sub-entity refs SET NULL) is followed everywhere with exactly **one** undocumented exception: `tact_conversation_message_attachments.attachment_id` uses `ON DELETE RESTRICT` (**P2**, functional not security, no comment explains the deviation). All CHECK-constraint enums (`WorkStatus`, `TaskStatus`, `RunStatus`, `ApprovalStatus`, `ClarificationStatus`, `ClarificationReasonCode`, `tact_audit_events.event_type`, `tact_execution_records.capability`) match their corresponding TypeScript unions exactly — no drift found. All expected unique/idempotency indexes are present and correctly targeted.

**The two P0/P1-severity RLS findings, already summarized above:**
1. **8 Legacy/Core tables run fully-open `using(true)`/`with check(true)` RLS** (`conversations`, `conversation_messages`, `conversation_workflow_runs`, `tact_execution_history`, `tact_memory`, `tact_core_knowledge`, `tact_core_memories`, `tact_core_examples`) — this was assumed low-risk on the theory that the Legacy engine is unreachable; **Section 15 disproves that assumption**, elevating this to a confirmed **P0**.
2. **No migration-drift verification mechanism exists anywhere** (no CI step, no script) — confirmed by direct search of `.github/workflows/`, `package.json`, and `supabase/.temp/` (which only records CLI project linkage, not applied-migration state). This is not hypothetical: this exact class of gap already caused the `tact_clarifications`/`tact_audit_events`/`allowed_approver_ids` production incident referenced in the audit brief. **P0.**

## 12. Audit/provenance findings (Phase 11)

`tact_audit_events` remains append-only by convention (no `updateAuditEvent()` exists, matches the P4a design decision); DB-enforced immutability (a Postgres `REVOKE UPDATE/DELETE` + trigger) is explicitly and knowingly deferred, as originally documented — **P3/DEFER, unchanged assessment**, no escalation warranted (no write path exists that could exploit the gap today; the risk is purely "a future bug could UPDATE a row," not a current one). Every emission site checked (`policy.evaluated`, `run.created/completed/failed`, `provider.called/completed/failed`, `approval.*`, `clarification.*`) follows the "audit failure must not break business path" principle — `emitAuditSafely()` swallows its own errors. The flip side the brief asks about — **is a swallowed audit failure fully silent, with no operational visibility at all?** — **yes, confirmed**: `emitAuditSafely()`'s failure path is a bare `console.warn`/similar, with no alerting, no retry-queue, no dead-letter record. If Audit writes started failing systematically (e.g., a schema drift on `tact_audit_events` — see Section 11's P0), the business logic would keep working *and nobody would be told the audit trail had gone dark*. **Severity: P2** (an observability gap, not a data-integrity one — canonical state itself is never at risk from this).

## 13. Artifact findings (Phase 12)

## 14. LLM/Agent/Research findings (Phase 13)

Full read by dedicated sub-agent. The Framework-inference/review pipeline (`core/tact-analysis/framework/**`) is a genuine structural no-fabrication implementation (numeric/proper-noun cross-check + second-LLM entailment review before anything is marked "supported"). **However, the primary Research answer text — what users actually see most often — has no equivalent check**: `contextAssembly.ts` tells the model its claims "will be mechanically cross-checked afterward," but `evidenceSupport.ts` only checks that cited evidence *IDs exist*, never that the answer's free text is actually entailed by them (confirmed by that file's own docstring, which explicitly disclaims semantic entailment checking). **This is an overclaiming prompt instruction with no matching enforcement — P2.** Local Workspace/attachment content injection is mitigated only at the prompt level (an inline "do not follow instructions in this content" instruction), not structurally — acceptable today because no LLM output in this scope drives an authorization-relevant action, but this would need to escalate to P0 if any future Capability lets LLM output trigger a write. ## 15. API route findings (Phase 15)

Full read of all 29 `app/api/**/route.ts` files by dedicated sub-agent. **This is where the audit's headline findings live.**

- **`app/api/tact/code-tasks/{run,approve,execute,commit,push,pull-request}/route.ts` and `code-tasks/route.ts` — P0, the single gravest finding in this audit.** Zero authentication anywhere in the entire family (confirmed independently by two sub-agents via direct grep — zero matches for any auth helper). `run` accepts free-text `instruction` and immediately invokes a real coding-agent adapter against the live server's own working directory; `execute` runs `execFile("npx","tsc",...)`; `commit`/`push` perform real `git commit`/`git push`; `pull-request` calls the `gh` CLI to open a real GitHub PR; `approve` is a bare, unauthenticated status flip that gates nothing of substance since the whole chain has no auth to begin with (contrast with `core/tact-work/approval.ts`'s `checkApproverAllowed()` self-approval/allowlist guard, entirely absent here); the collection `GET` discloses full task records (repository path, instructions, stdout) to anyone who supplies or enumerates an id. `code-tasks/run` is wired into the shipped UI (`components/tact/CodeSection.tsx` inside `TactShell.tsx`), so this is not a stray unreachable file. `core/codeAgent/store.ts` has no `userId`/owner field at all — this isn't a caller-supplied-userId problem, it's the total absence of an authorization concept to retrofit onto.
  **Compounding, independently-discovered command-injection defect**: `core/codeAgent/gitProvider.ts:434,484` calls `execFile("gh", [...], { shell: true })` for `gh pr create`, passing `--title`/`--body`/`--base` **directly from unsanitized request-body fields** (`app/api/tact/code-tasks/pull-request/route.ts:73-80`). This is materially inconsistent with this same codebase's own documented mitigation one file over — `core/codeAgent/claudeCodeAdapter.ts`/`codexAdapter.ts` explicitly keep all dynamic content off the CLI argv (piped via stdin instead) specifically citing awareness of **CVE-2024-27980** (Node `shell:true` + Windows `.cmd`/`.bat` argv-injection), yet the `gh` CLI call uses `shell:true` with attacker-controlled argv content anyway. Combined with zero authentication on the route in front of it, this is not merely "unauthorized access to a feature" — it is an unauthenticated command-injection-shaped RCE vector. `runGit()`'s own git operations (`status`/`branch`/`diff`/`add`/`commit`/`push`) correctly avoid `shell:true` and are not implicated by this specific sub-finding.
- **`app/api/tact/route.ts` (POST) / `app/api/tact/stream/route.ts` (GET) — P0** (jointly with Section 11's finding #1): zero auth, invoke the Legacy `core/workflow` engine, real LLM cost per call, `stream` uses GET for a paid side-effecting operation. Paired with `app/legacy/page.tsx` and `app/test/page.tsx`, both of which are ordinary, unguarded, production-served Next.js pages.
- Every route with a genuine per-user resource concept (`projects/**`, `tact-conversations/**`, `artifacts/**`, `runtime/reconcile`, `core/push`, `knowledge`, `improvement-proposals`) correctly derives `userId` from `getCurrentUserContext(request)`/the Authorization header only, never from the request body — the STEP131 discipline is followed with **zero exceptions found** among routes that have an ownership concept at all.
- IDOR check: every by-ID route re-verifies ownership server-side before returning/mutating data, **with one narrow, already-acknowledged, by-design exception**: the *Legacy* (non-`tact-` prefixed) `conversation`/`conversations` routes permit indefinite access to a conversation created without auth (`userId: null`) by anyone who knows its UUID — low likelihood (UUIDs aren't enumerable) but unmitigated by any rate limiting. **P2.**
- Intentionally-unauthenticated-by-design routes (`chat`, `research`, `conversation`, `conversation/stream`, `attachments`) are a deliberate, documented tradeoff (anonymous usage is a supported feature), but **no route anywhere in `app/api/**` has any rate limiting** — confirmed by direct search — so the cost/DoS exposure on these routes (already compounded by Section 14's unbounded-query finding for `research`) is currently unmitigated. **P2.**
- `middleware.ts` does not exist — there is no repo-wide choke point that could have caught any of the above centrally; every route is independently responsible for its own auth.

## 18. Test gaps (Phase 18)

157 test files, all mock/fake-based by explicit design (`tests/tact/lib/check.ts`'s own header: "LLM call = 0 / Search API call = 0"). This is a deliberate, sound choice for a fast regression suite, but it has structural blind spots this audit is asked to name explicitly:

- **RLS is never exercised by any automated test.** All 21 migrations' policies (Section 11) are verified only by manual/sub-agent file reading in this audit, never by a test that actually connects to Postgres and confirms a policy behaves as written. A typo in a future `auth.uid()` policy would not be caught by `npm test`.
- **Concurrency**: only 1 of 157 files uses `Promise.all` for a genuine race test (this session's own `taskResumeExecution.test.ts`). Slack dedup, Approval double-click, and reconciliation "concurrent invocation" are all covered only by sequential-call tests, despite this audit's own analysis (Section 5) concluding the underlying DB-index mechanisms would very likely hold — that conclusion rests on code inspection, not on a passing concurrent test.
- **Real Production webhook**: `bot/receiveApprovalDecision.test.ts`/Slack signature tests exercise the fail-closed-when-unconfigured path only (the 2 known `SLACK_SIGNING_SECRET` failures) — no test constructs a real signed Slack payload end-to-end to confirm the *success* path.
- **Migration compatibility**: no test loads the actual `.sql` files against a real or in-memory Postgres to confirm they apply cleanly in order (this is a different, narrower gap than Section 11's "is production up to date" finding — this one is "do the migrations even apply cleanly at all, ever, automatically checked").
- **Cross-workspace/cross-tenant isolation**: covered by code-level assertions in the identity-resolution test suite, not by a dedicated adversarial test that simulates two different Slack workspaces colliding.
- **Partial success / compensation**: no test exercises a multi-Task Work where some Tasks succeed and others fail, confirming what the user actually sees (Section 21 discusses this as a design gap, not just a test gap).
- **Re-evaluating the 2 known `SLACK_SIGNING_SECRET` failures**: confirmed, on this pass, that they are exactly what they claim to be — a precondition check that the *local test environment* doesn't have the secret set, followed by a direct assertion that the real `handleSlackWebhookRequest()` fails closed (401) when unconfigured. This is not a broken test; it is deliberately unresolvable in an environment without the secret, and it correctly narrows to a fail-closed-path assertion rather than skipping silently. **No re-classification needed — still an acceptable, known, non-blocking exception.**

**Overall Test Quality classification: solid regression coverage for the canonical Work/Task/Run/Policy/Approval/Runtime/Reconciliation architecture (extensively exercised, including this session's own new concurrency tests); near-zero coverage for RLS, real concurrency beyond one file, and the Legacy/code-tasks periphery where this audit's worst findings live** — consistent with those periphery areas being unauthenticated: nobody wrote tests for authorization on routes that have none.

## 21. Practical multi-SaaS readiness (Phase 21)

Traced the brief's own example Work end-to-end against current code (no code written, pure trace):

> "Check recent emails and materials from Company A, save next meeting's discussion points to Notion, check next week's availability and reply on Slack."

1. **No capability exists for Gmail/Notion/Drive/Calendar today** — `POLICY_ALLOWLIST` has exactly one service (`slack`), Composio adapter mappings exist only for Slack, and `createConnection()`/`createSlackConnectionLink()` (the only OAuth-connection-creation code that exists at all) have **zero live callers anywhere in the app** (confirmed earlier in this session's own P5d investigation) — connecting a new service today requires building the Connection UI/OAuth flow from scratch, not just adding a Policy entry.
2. **No rich, multi-turn "search my email for X" capability model exists** — today's Integration model is shaped for simple, single-shot actions (`list_channels`, `send_message`). "Check recent emails about Company A" is a *search/retrieval* task, architecturally closer to the explicitly-DEFERRED "Organizational Context / enterprise search (Glean-class)" capability named in `p2-p5-final-architecture.md` than to the existing read/write Integration model. **This is the single largest capability gap for the stated scenario** — not a bug, a not-yet-built capability.
3. **No partial-success/compensation semantics**: `reconcileWorkCompletionStatus()` is binary — any failed Task fails the whole Work. A 4-step cross-SaaS Work where 3 steps succeed and the 4th fails (e.g., Notion write rejected) reports the entire Work as `"failed"`, even though 3 real actions already happened with real external side effects that cannot be automatically undone (no compensation/rollback concept exists anywhere in the architecture). The user may still see partial results in chat text (individual read results are surfaced inline), but any code/dashboard reading canonical `Work.status` as ground truth would see only `"failed"`. **P2.**
4. **Resume correctly scopes per-Task** — an Approval resolving on the Notion-write step does not risk re-triggering the already-completed Gmail-read step (`requestTaskResume()`/`executePreparedTaskResume()` are `taskId`-scoped, verified this session). No new gap here.
5. **No Artifact-to-Provider export pipeline exists** — "save discussion points to Notion" would need custom glue to read Artifact block content and pass it as literal string input to a (not-yet-built) Notion-write action; there is no existing "take this Artifact and push it to a provider" mechanism (Section 13).
6. **No Approval/Clarification expiry enforcement** (Section 6) — realistic for a real "the user comes back in three days" cross-SaaS Work; a stale Approval could be actioned long after context is lost.
7. **The stranded-Task window (Section 4)** becomes more consequential, not less, as Work complexity grows: a 5-Task, 4-provider Work has 5x the crash-window exposure of a single-Task Work.

**Conclusion for this section: readiness is currently gated primarily on missing capability build-out (items 1–2, expected and not itself a defect) rather than on architectural correctness (items 3–7 are real gaps, but P1/P2, not P0) — with the explicit caveat that none of this should be attempted before the Section 15 P0s are closed, since new SaaS write capability directly increases the blast radius of the already-open unauthenticated code-execution and Legacy-engine exposure.**

**TACT Pre-Live Full Repository Audit = PASS WITH REQUIRED FIXES.**
