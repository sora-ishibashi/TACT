# Problem Solved

In AXME's own words (from the `axme` repo README and product pages): AI agents that need a human decision **"block forever waiting for human approval — no reminders, no escalation, session dies"**. AXME's stated goal is to let **"agents, services, and humans coordinate as equals"** through a durable **Intent** abstraction: a caller "submits once", the platform tracks the intent's lifecycle durably (surviving process crashes, restarts, and long human wait times), and the caller "completes later" without needing to keep a process/HTTP connection alive or hand-roll polling/webhook/retry glue. It is explicitly positioned as a lighter-weight, agent/human-approval-focused alternative to running a full workflow engine cluster (the README compares it to Temporal, claiming "4 lines of code versus 80–200").

Concretely, it targets three coordination pain points named in the docs: (1) durable execution across agent crashes/restarts, (2) human-in-the-loop steps that may need to "wait hours not minutes" with reminders/escalation instead of a short timeout, and (3) multi-agent handoff/coordination "across services, languages, and clouds" via a common protocol (AXP) rather than a framework-specific mechanism (they explicitly call out LangGraph, CrewAI, AutoGen, and the A2A protocol as things AXP adds durable lifecycle/retries/timeouts/human checkpoints on top of).

# Architecture

- **Core concepts**: *Intent* (one submitted, durably tracked unit of work with its own lifecycle state machine), *Session* (an orchestrator entity that can spawn/group multiple intents — `session_id` / `parent_intent_id` fields), *Envelope* (the wire wrapper around a payload: `version`, `intent_type`, `intent_id`, `correlation_id`, `idempotency_key`, `from_agent`, `to_agent`, `payload`, `session_id`, `metadata` — see `schemas/protocol/intent.envelope.v1.json`), *delivery binding* (how a participant receives an intent: `stream` (SSE), `poll` (`GET /v1/intents?status=pending`), `http` (webhook push with HMAC signature), `inbox` (human-facing queue: CLI/email/forms), `internal` (platform-internal step, no external agent)).
- **Main entities** (from schema file names and docs): Intent, Session, Message (envelope v2/v3), Inbox thread, Approval, AccessRequest. Confirmed schema files: `intent.envelope.v1.json`, `intent.lifecycle.v1.json`, `intent.event.v1.json`, `intent.ask.v1.json`, `intent.error.v1.json`, `intent.reply.v1.json`, `intent.status.v1.json`, `message.envelope.v2.json`/`v3.json`, `message.delivery.v1.json`, `session.envelope.v1.json`, `session.event.v1.json`, `session.lifecycle.v1.json` (all under `AxmeAI/axp-spec/schemas/protocol/`). Public API schemas (under `schemas/public_api/`) include `api.approvals.decision.request/response.v1.json`, `api.inbox.decision.request.v1.json`, `api.inbox.delegate.request.v1.json`, `api.inbox.list/thread/reply/changes.*.v1.json`, `api.access_requests.create/review/list/get.*.v1.json` (~90+ endpoint schema files total per the schema index doc; not all individually enumerated here).
- **State machine**: See dedicated section below — directly confirmed via `schemas/protocol/intent.lifecycle.v1.json` and `schemas/protocol/intent.event.v1.json`.
- **Execution model**: Explicitly **event-sourced**, per `docs/ADR-006-intent-lifecycle-v1.md`: "State transitions occur through dedicated `intent.*` events"; "Lifecycle progression is observable through state and events, not RPC semantics." Each intent carries a monotonic per-intent `seq` (sequence number) that increments with every lifecycle event, used for ordering/resumability. The spec also explicitly supports "handler transfers without status changes" (an `intent.transfer` event type) — i.e. reassigning who is working an intent without changing its lifecycle status.
- **Persistence model**: Not directly inspectable — the actual runtime/database implementation is **not in the public repos** (the `axme` repo contains only README/docs/license/community files, no source code; the actual durable-execution backend is the closed-source "AXME Cloud" managed service). What is confirmed is the *shape* of persisted state (from the JSON Schemas): `intent_id`, `correlation_id`, `status`, `seq`, `created_at`, `updated_at`, optional `timeout_at`, `handler`, `handler_version`, `waiting_reason` (required when `status == WAITING`), optional `session_id`/`parent_intent_id`, and an open `metadata` bag. The actual storage engine, transaction model, and multi-tenant isolation are **未確認 (unconfirmed)** — reasonable to infer some durable store exists given the "survives restarts" claims, but no evidence of which technology.
- **Human interaction model**: AXME advertises **8 built-in "human task" types**: `approval`, `review`, `form`, `manual_action`, `override`, `confirmation`, `assignment`, `clarification` (stated in the `axme` README and corroborated by the `internal` runtime-step list in the spec's schema index, which also separately lists automated internal steps `human_approval`, `timeout`, `reminder`, `delay`, `escalation`, `notification`). The most basic "ask a human something" payload shape is `intent.ask.v1.json`: `{question (string, required), context (string, optional), deadline_at (date-time, optional), requested_by (required), requested_at (required), workflow (open object, optional)}`. Humans interact via the `inbox` delivery binding (CLI/email/forms) and via dedicated REST endpoints: `POST /v1/approvals/{approval_id}/decision` (`api.approvals.decision.request.v1.json` — body is simply `{decision: "approve"|"reject", comment?: string}`), plus inbox-scoped `POST /v1/inbox/{thread_id}/approve|reject|delegate|reply` and access-request review endpoints (`POST /v1/access-requests/{access_request_id}/review`).
- **Retry / recovery**: Documented in `docs/idempotency-correlation-rules.md`. Three identifiers: `intent_id` (unique per message/event), `correlation_id` (stable across all messages/events in one logical workflow — "all status and error events must be attributable to the same correlation_id"), `idempotency_key` (client-generated, optional in the envelope, required for external side-effecting writes). Dedup key = composite of **sender identity + endpoint + idempotency token**; a repeat of the same key returns the original result; the **same key with a different payload is treated as a conflict** (rejected, not silently overwritten). Minimum recommended cache retention for dedup records: **24 hours (MVP)**. Retry guidance: validation/auth failures are not retryable with the same payload; transport/timeout errors may be retried reusing the same `idempotency_key`+`correlation_id` pair.
- **Permission / policy**: `policy_denied` is a first-class, non-retryable error code (`docs/protocol-error-status-model.md`). ADR-004 names a `policy_engine` as one of Axme's own backend services (alongside `gateway`, `agent_core`, `integrations`), kept separate from the transport layer (Matrix/Synapse). There are also `access_requests` create/review/list/get API schemas implying an access-request-and-adjudication flow. **The actual policy engine's decision logic/rules are not in the public repos** — this is REFERENCE_ONLY (naming/shape of the concept, not an implementation).
- **Audit**: The event-sourced `intent.event.v1.json` schema (see below) is itself the closest thing to a built-in audit trail: every lifecycle transition, reminder, escalation, delivery failure, transfer, and human-task-assignment is a discrete, ordered (`seq`), timestamped (`at`), optionally actor-attributed (`actor`) event. No separate "audit log" schema distinct from this intent-event stream was found.
- **Credential handling**: `docs/ADR-005-matrix-transport-e2ee-rollout.md` states service-account device keys "require encryption before storage, with KMS/HSM wrapping the key hierarchy," and that "Rotation and recovery flows are mandatory release criteria." Message bodies use Matrix's native E2EE stack (Olm/Megolm) with an explicit prohibition on plaintext storage in Matrix mode and no custom parallel ciphertext protocol.
- **Provider/runtime coupling**: This is a significant, concrete architectural finding. Per `docs/ADR-004-synapse-no-modification-policy.md` and `docs/ADR-005-matrix-transport-e2ee-rollout.md`, AXME's transport layer is built on **Matrix protocol / Synapse** (the Matrix.org reference homeserver), used **unmodified** ("Use official upstream Synapse image as-is for MVP. Do not modify Synapse source code.") — a "hard cutover" making Matrix "the sole transport mechanism for non-MCP message delivery paths," with native E2EE (Olm/Megolm). Business logic is required to live in Axme's own services (`gateway`, `agent_core`, `policy_engine`, `integrations`), never inside Synapse. Separately, the actual **durable-execution runtime that drives an Intent to completion is "AXME Cloud," a closed-source managed SaaS** — the worked example repo (`async-human-approval-for-ai-agents`) confirms this: its architecture is `Agent → send_intent() → AXME Cloud → Notify Human → wait_for() → Resume`, i.e. the runnable open-source example is a thin client calling out to the proprietary cloud backend, not a self-hostable engine.

# State Machine

**Implemented** (directly confirmed by fetching the raw JSON Schema files, the closest thing to authoritative "code" in AXME's public repos):

- `status` enum (`schemas/protocol/intent.lifecycle.v1.json`, also mirrored in `intent.event.v1.json`):
  `CREATED`, `SUBMITTED`, `DELIVERED`, `ACKNOWLEDGED`, `IN_PROGRESS`, `WAITING`, `COMPLETED`, `FAILED`, `CANCELED`, `TIMED_OUT` (10 values).
- `waiting_reason` enum (required whenever `status == WAITING`, enforced via a JSON Schema `if/then`): `WAITING_FOR_HUMAN`, `WAITING_FOR_TOOL`, `WAITING_FOR_AGENT`, `WAITING_FOR_TIME`.
- `event_type` enum (`schemas/protocol/intent.event.v1.json`): `intent.created`, `intent.submitted`, `intent.delivered`, `intent.acknowledged`, `intent.in_progress`, `intent.waiting`, `intent.completed`, `intent.failed`, `intent.canceled`, `intent.transfer`, `intent.timeout`, `intent.timed_out`, `intent.reminder`, `intent.escalated`, `intent.delivery_failed`, `intent.human_task_assigned`.
- Every intent event carries a monotonic `seq` (integer ≥ 1) and a required timestamp (`at`), plus optional `actor`, `handler`, `session_id`.
- `intent.error.v1.json` / `docs/protocol-error-status-model.md` error codes with explicit retryability flags: non-retryable = `agent_not_found`, `invalid_agent_address`, `schema_invalid`, `auth_failed`, `policy_denied`; retryable = `delivery_failed`, `intent_timeout`, `internal_error` (+ implementation-defined codes matching `^[a-z0-9_:.\-]{3,128}$`).

**Inferred** (described in docs/README prose but not verified as literal enum/code — or summarized by an intermediate fetch rather than the raw file):
- The exact allowed transition graph between states (e.g. "`SUBMITTED` → `DELIVERED`/`IN_PROGRESS`/`WAITING`/`FAILED`/`CANCELED`") — this came back as prose from `docs/intent-lifecycle-v1.md` via an automated fetch/summarize step, not as a machine-checkable transition table; treat the specific edge list as **directionally credible but not independently re-verified**.
- Whether `TIMED_OUT` is itself a further terminal state distinct from `FAILED`, or a specialization of it — the schema lists it as a separate enum value and `intent.event.v1.json` has both `intent.timeout` and `intent.timed_out` as distinct event types, but the precise semantic difference between the two event types was not found spelled out in the fetched docs.
- Whether the real AXME Cloud runtime actually implements this exact state machine faithfully — the spec is normative documentation for the protocol, but the runtime itself is closed-source, so conformance cannot be directly verified from public repos (an `axme-conformance` test-suite repo exists specifically to check spec/runtime/SDK parity, which itself implies this gap is a known concern for the project, but the test results are not public).

# TACT Equivalent

- **Work**: AXME's **Session** (an orchestrator that groups multiple related Intents via `session_id`/`parent_intent_id`, `session.lifecycle.v1.json`) is the closest analog to TACT's `Work` — a container above the individual unit of durable execution. AXME's `correlation_id` ("stable across all messages/events in the same logical workflow") plays a similar cross-cutting-identifier role to how TACT keeps `Work.id` distinct from `Conversation.id`.
- **Task / Run**: AXME's **Intent** most closely maps to TACT's `Task` (a submitted, durably tracked logical unit of work with its own lifecycle) — but AXME does **not** cleanly separate "Task" from "one execution attempt" the way TACT splits Task→N Runs. Instead, retry-safety is handled at the Intent level via `idempotency_key`/`correlation_id` dedup, not by spawning a distinct child "Run" entity per attempt. This is a genuine architectural difference worth noting, not a 1:1 match — do not force Intent = Run.
- **HumanInteraction**: This is the strongest correspondence found. AXME's **8 built-in human task types** — `approval`, `review`, `form`, `manual_action`, `override`, `confirmation`, `assignment`, `clarification` — are an almost direct naming match to TACT's own proposed (not-yet-implemented) generalization list: Approval / Selection / Clarification / Review / Assignment / Confirmation / ManualAction. AXME has no explicit `override` or `form` in TACT's list, and TACT's `Selection` has no obvious explicit counterpart in AXME's named list (it may be intended to be expressed via `form` or `clarification`, but this is not confirmed). This convergence is useful external validation that this particular decomposition of "human interaction" is a reasonable one, independently arrived at.
- **Approval**: AXME's `approval` human task type + `POST /v1/approvals/{approval_id}/decision` (`decision: "approve"|"reject"`, `comment?`) is a narrow, minimal, directly comparable schema to what TACT would need for its own Approval type.
- **Participant/Capability**: AXME's envelope (`from_agent`/`to_agent` as plain string identities) does **not** give Agent/Service/Human distinct typed entities at the core protocol level — the human/agent/service distinction lives in *which delivery binding* is used (`inbox` for humans vs `stream`/`poll`/`http` for agents/services), not in a typed "Participant" field in the schema itself. This is a notable finding relative to TACT's ambition to treat Agent/Service/Human as the same "participant" abstraction: AXME achieves "coordinate as equals" more at the *transport/delivery* layer than via a first-class unified Participant *entity type* in its wire schema. TACT's own explicit Participant/Capability abstraction is arguably more structured than what AXME's public schemas show.
- **Waiting state / durable execution**: AXME's `WAITING` status + mandatory `waiting_reason` (`WAITING_FOR_HUMAN`/`_TOOL`/`_AGENT`/`_TIME`), event-sourced (not blocking-connection-based), is a directly relevant reference pattern for TACT's stated goal of decoupling Work lifecycle from HTTP request lifetime (durable execution) — this is the single most concretely reusable *design pattern* (not code) for TACT here.
- **Audit**: AXME's `intent.event.v1.json` event stream (ordered via `seq`, timestamped, actor-attributed) is conceptually aligned with TACT's Audit responsibility — an append-only, ordered event log per unit of work.
- **Permission/Policy/Approval enforcement point**: AXME names a separate `policy_engine` service and a non-retryable `policy_denied` error code, which is directionally consistent with TACT's requirement that policy/permission decisions be enforced deterministically at the execution layer rather than via LLM judgment — but since AXME's policy engine implementation is closed-source, this can only be cited as a naming/shape precedent, not as evidence of *how* to implement deterministic policy enforcement.
- **Idempotency/dedup**: AXME's idempotency-key + correlation-id composite dedup with "same key + different payload = conflict" is directly relevant to TACT's "a successful external side effect must never be casually re-executed" requirement — a genuinely reusable *pattern* (not code, since the enforcement logic itself is not in the public repos).
- **Context/Provider neutrality**: No direct correspondence found; AXME's protocol is provider-neutral in principle (framework-agnostic language: LangGraph/CrewAI/AutoGen/raw Python), but its *transport* is hard-committed to Matrix/Synapse (see Risks), which is itself a form of infrastructure lock-in TACT would want to avoid replicating uncritically.

# Reusable Schema

- **Intent envelope shape** (`intent.envelope.v1.json`): `version`, `intent_type` (pattern `^intent\.[a-z0-9_]+\.v1$`), `intent_id` (uuid), `correlation_id` (uuid), `idempotency_key` (8–128 chars), `created_at`, `from_agent`, `to_agent`, `payload` (open object), optional `session_id`, `metadata` (string-valued map). Clean, minimal, directly portable *conceptually* to a TACT `Task`/`Work` envelope — small enough to reimplement from scratch in TACT's own types rather than import, but useful as a checklist of fields TACT might be missing (e.g. an explicit `idempotency_key` distinct from any internal DB id).
- **Lifecycle status enum + waiting-reason conditional requirement** (`intent.lifecycle.v1.json`): the pattern of "`WAITING` is a single status, but a `waiting_reason` sub-enum is mandatory whenever status is WAITING" (enforced via JSON Schema `if/then`) is a clean, borrowable *schema pattern* for TACT's own future Work/Task status representation, regardless of the exact state names TACT chooses.
- **Event schema** (`intent.event.v1.json`): `intent_id`, `seq` (monotonic per-intent), `event_type` (closed enum incl. `*.reminder`, `*.escalated`, `*.transfer`, `*.human_task_assigned`, `*.delivery_failed`), `status`, `at`, optional `actor`/`handler`/`session_id`/`payload`/`metadata`. This is a good reference shape for an Audit/event-log schema — the explicit `escalated`, `reminder`, `transfer`, `human_task_assigned` event types are a useful vocabulary check against TACT's own planned Assignment/Escalation concepts.
- **Human-ask payload** (`intent.ask.v1.json`): `question`, `context?`, `deadline_at?`, `requested_by`, `requested_at`, `workflow?` — a minimal, genuinely reusable shape for TACT's planned `Clarification`/`Approval` request payloads.
- **Approval decision payload** (`api.approvals.decision.request.v1.json`): `{decision: "approve"|"reject", comment?}` — about as small a reusable schema as exists; trivially reimplementable in TACT's own types.
- **Error model** (`protocol-error-status-model.md`): closed set of error codes each tagged retryable/non-retryable, with a `^[a-z0-9_:.\-]{3,128}$` extension pattern for implementation-defined codes — a reasonable reference shape for a TACT execution-error taxonomy, though TACT would need its own code list (AXME's is protocol/transport-flavored — `agent_not_found`, `invalid_agent_address` — not directly TACT's domain).
- Everything above is schema (JSON Schema documents), MIT-licensed in the `axp-spec` repo, so there is no licensing barrier to reading/adapting the *shapes*; note none of it is TACT-schema-compatible as-is (different field names/conventions) and would need to be rewritten in TACT's own type system (Zod/TypeScript), not imported wholesale.

# Reusable Pattern

- **Single canonical `WAITING` status with a mandatory, closed-enum `waiting_reason`** rather than many bespoke "pending_x" statuses — keeps the top-level state machine small while still being queryable/groupable by *why* something is waiting. Directly relevant to TACT's future work on decoupling Work lifecycle from HTTP request lifetime.
- **Idempotency-key + correlation-id composite dedup, with "same key + different payload ⇒ conflict, not silent overwrite/no-op"** — a concrete, precise rule TACT can adopt verbatim as a policy statement for its own "no casual re-execution of a successful external side effect" requirement.
- **Event-sourced lifecycle with a monotonic per-intent sequence number**, explicitly justified in ADR-006 as making "lifecycle progression observable through state and events, not RPC semantics" — aligns with TACT's Audit ownership goal and durable-execution ambitions.
- **Delivery-binding-as-the-place-participant-type-lives** (stream/poll/http for agents & services, inbox for humans, internal for platform-internal steps) rather than a typed Participant field on every message — an interesting *alternative* design choice to weigh against TACT's stated intent to give Agent/Service/Human a shared Participant abstraction; worth an explicit decision either way rather than adopting silently.
- **"Handler transfer without a status change"** (`intent.transfer` event) — a pattern for reassignment/hand-off that doesn't need to be modeled as a state-machine transition, potentially relevant to TACT's future Assignment concept.

# Risks

- **License**: MIT on the inspected repos (spec, main landing repo, example repo) — permissive, no blocking concern for reading/referencing. However the *actual runtime* (AXME Cloud) has no visible license because it is not published as source at all — nothing runtime-related can be classified as REUSE regardless of the spec's license.
- **Security**: Cannot be assessed beyond ADR-level claims (KMS/HSM key wrapping, Olm/Megolm E2EE) — no implementation was inspectable. Treat all security claims as vendor-asserted, not independently verified.
- **Provider lock-in**: The actual durable-execution engine is a closed-source, single-vendor managed cloud ("AXME Cloud"). Adopting AXME as infrastructure (not just as a reference) would mean depending on a single small vendor for the core durability guarantee.
- **Runtime lock-in**: The transport layer is hard-committed to Matrix/Synapse per ADR-004 ("hard cutover", "sole transport mechanism", official upstream image only, no modification permitted for MVP) — this is a real, documented lock-in decision *within AXME itself*, and a cautionary example: it shows how quickly "borrow first" can turn into deep coupling if the borrowed dependency becomes load-bearing for the transport layer rather than staying swappable.
- **Architecture mismatch**: AXME's Intent does not cleanly separate Task (logical unit) from Run (execution attempt) the way TACT's canonical model does — forcing a 1:1 mapping would lose information TACT explicitly cares about (N runs per task, provider neutrality per run).
- **Agent-centric bias**: Despite the "equals" framing, the concrete wire schema (`from_agent`/`to_agent`, `agent_not_found`, `invalid_agent_address` error codes) is agent/address-centric in its naming; the human/service distinction is realized operationally (via delivery binding) rather than in a first-class typed field, which is a softer form of agent-centric bias worth noting given TACT's explicit goal of a truly uniform Participant abstraction.
- **Overengineering**: The transport-layer commitment to a federated chat protocol (Matrix, with full E2EE/Olm/Megolm/KMS/HSM key rotation machinery) for what is fundamentally a workflow-orchestration/approval product looks like a heavyweight, possibly premature architectural bet for a pre-1.0/3-star project — a risk pattern (not a recommendation) worth flagging for TACT's own "Build less" discipline.
- **Scaling concern**: No evidence either way (closed-source runtime); cannot assess.
- **Persistence mismatch**: Persistence technology is entirely unconfirmed (closed-source runtime) — cannot compare against Supabase-as-source-of-truth requirement.
- **Multi-tenant concern**: No evidence of multi-tenancy model in the public schemas/docs — unconfirmed.
- **Secret handling**: Only ADR-level claims (KMS/HSM wrapping of Matrix device keys) — no inspectable implementation; do not treat as a verified pattern to copy, only as a design intent to be aware of.
- **General maturity risk**: 3 stars / 0 forks / ~1 month of active pushes / Alpha (v0.1.2) SDKs — this is a very early, low-adoption project. Findings here should be weighted as "one team's fresh design thinking," not as a battle-tested reference architecture.

# Classification

- **Intent/Work lifecycle state machine shape** (status enum + mandatory waiting_reason + event-sourced transitions): **ADAPT** — good conceptual pattern, reimplement in TACT's own types, do not import.
- **Human task type taxonomy** (approval/review/form/manual_action/override/confirmation/assignment/clarification): **REFERENCE_ONLY** — valuable as an independent cross-check against TACT's own proposed Approval/Selection/Clarification/Review/Assignment/Confirmation/ManualAction list; do not adopt AXME's exact 8 names wholesale, but do compare against them explicitly.
- **Idempotency/correlation dedup rule**: **ADAPT** — the specific rule ("same key, different payload ⇒ conflict") is precise and worth adopting as written, but as a policy statement in TACT's own execution layer, not as imported code.
- **JSON Schema field shapes** (envelope, ask, approval-decision, error model): **REFERENCE_ONLY** — useful as a checklist while designing TACT's own schemas; MIT license permits closer reuse if ever desired, but field-by-field porting is not recommended given naming/convention mismatches with TACT's canonical domain types.
- **Actual runtime/source code**: **REJECT** for reuse — none is public; nothing to import.
- **Matrix/Synapse transport dependency**: **REJECT** — do not adopt this as a TACT dependency; noted only as a cautionary architecture example.
- **Participant abstraction (Agent/Service/Human unification)**: **REFERENCE_ONLY, with a caution** — AXME's approach (unify at delivery-binding layer, not at entity-type layer) is a real alternative design to be aware of, not a validated best practice to copy; TACT's own more explicit typed-Participant direction is not shown to be wrong by this comparison.

# Recommendation

## Adopt
- The **status + mandatory-waiting_reason** schema pattern as a conceptual reference when TACT designs its own durable Work/Task waiting-state representation.
- The **idempotency-key + correlation-id, conflict-on-payload-mismatch** dedup rule as an explicit policy statement for TACT's execution layer.
- Use AXME's **8-type human-task taxonomy** as a cross-check/comparison point (not a source of truth) the next time TACT's team formally discusses generalizing Human Interaction into Approval/Selection/Clarification/Review/Assignment/Confirmation/ManualAction — specifically worth discussing whether TACT needs an explicit `Override` or `Form` type of its own, since AXME has both and TACT's current list does not.

## Do Not Adopt
- AXME's runtime, SDKs, or any code as a dependency — the actual durable-execution engine is closed-source SaaS, which would reintroduce exactly the kind of vendor lock-in TACT's "Provider neutrality is a hard requirement" principle exists to prevent.
- AXME's Matrix/Synapse transport-layer design — this is a lock-in risk pattern to avoid replicating, not a pattern to borrow.
- Any 1:1 mapping of Intent → Run — it would lose TACT's Task/Run (1→N) distinction.

## Why
AXME is a real, identifiable, small/early-stage OSS + managed-cloud project (AxmeAI, MIT-licensed protocol spec, 3 stars, ~6 months old) whose stated problem space — durable intent lifecycle, agents/services/humans "as equals," human-in-the-loop approval with reminders/escalation, waiting states — matches the investigation brief closely enough that its design vocabulary (not its code, which is largely unavailable) is a genuinely useful sanity-check for TACT's own in-progress Human Interaction generalization design. Its low maturity and closed-source runtime mean it should inform TACT's thinking rather than supply components.

No code-level Phase is warranted — this document itself is the deliverable; no `core/` changes are implied or recommended by this investigation.
