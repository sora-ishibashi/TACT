# Problem Solved

In Preloop's own words (README / docs.preloop.ai): organizations running AI agents (Claude Code, Codex CLI, Cursor, Gemini CLI, OpenClaw, Hermes, OpenCode, Windsurf, or any MCP-compatible agent) currently need to buy and stitch together separate vendor tools for (a) controlling which tools/actions an agent may invoke, (b) controlling and attributing LLM/model spend, (c) requiring a human to approve risky actions, (d) observing what an agent session actually did, and (e) producing an audit trail — "requiring separate purchases from specialized vendors." Preloop's stated goal is to be a single self-hostable "AI agent control plane" that unifies these: an **MCP firewall** (tool-call gating), an **AI model gateway** (budgets/attribution/allowlisting for OpenAI/Anthropic-compatible traffic), **policy-as-code** (YAML + CEL), **human approvals** (mobile/Slack/Mattermost/email/webhook), **runtime session observability**, and **audit trails** — plus an event-driven "Flows" layer that reuses the same governance/cost controls for automations triggered by GitHub/GitLab/Jira/webhooks. It explicitly targets the "govern many different coding/ops agents you don't want to trust blindly" problem, not a general workflow-orchestration problem.

# Architecture

- **Core concepts** (from `ARCHITECTURE.md` and docs):
  - MCP Firewall: an MCP-native policy engine — it exposes its own MCP endpoint (`/mcp/v1`) that agent clients connect to instead of connecting to the real MCP server directly; Preloop then proxies to the underlying tool.
  - Model Gateway: an "OpenAI- and Anthropic-compatible" HTTP ingress in front of real model providers, adding accounting, budgets, allowlisting, and "runtime session identity."
  - Policy-as-code: YAML policy documents with ordered/prioritized rules, each rule optionally using a CEL (Common Expression Language) condition, producing one of a small set of actions.
  - Preloop Console: a Lit/Vite/TypeScript/Shoelace web frontend.
  - Preloop Sync / Flows: a scheduler+worker layer (NATS-coordinated) that polls issue trackers (Jira/GitHub/GitLab) and runs event-driven automations ("Flows") under the same governance.
  - `preloop agents discover`: a CLI mechanism that finds local agent configs (e.g. Claude Code, Cursor config files) and rewrites them to route tool calls and model traffic through Preloop.
- **Main entities** (inferred from `backend/preloop/models/models/` and `backend/preloop/schemas/`, file names only unless noted): `Account`, `User`, `Organization`, `Team`, `ApiKey`, `ToolConfiguration`, `ApprovalWorkflow`, `ApprovalRequest`, `ApprovalEvent`, `ApprovalBypass`, `ToolApprovalCondition`, `PolicySnapshot`, `PolicyVersion`, `AuditLog`, `Event`, `AiModel`/`AiModelPricing`, `GatewayUsage`/`ApiUsage`, `Issue`/`IssueLifecycle`, `FlowExecution`, `KillSwitch` (scoped state, not a standalone ORM file — modeled via `KillSwitchScopeState`/`KillSwitchStatus` in `backend/preloop/schemas/kill_switch.py`).
- **State machine**: see dedicated section below.
- **Execution model**: Tool calls from an MCP client arrive at Preloop's `/mcp/v1` HTTP endpoint and are handled by `DynamicMCPServer.handle_call_tool` (`backend/preloop/services/dynamic_mcp_server.py`). That handler calls an internal `_evaluate_policy`, which in turn calls `evaluate_policy_async` in `backend/preloop/services/policy_evaluator.py` (sync entry point: `evaluate_policy(db, tool_name, tool_args, account_id, tool_configuration_id, user_id, execution_id, trigger_event, subject_context) -> PolicyDecision`). Rules are evaluated **in priority order (lower priority number first)**; the **first matching rule wins**; if no rule matches, the **default is `allow`**. Conditions support both simple field/regex comparisons and full CEL expressions (via the `celpy` library). If policy evaluation itself fails/errors, the code **fails closed**: it returns `require_approval` rather than allowing the call through — this is an explicit fail-safe design choice worth noting for TACT.
- **Persistence model**: PostgreSQL + PGVector (vector search used for duplicate-issue/compliance detection, not for policy). Alembic migrations (`backend/preloop/models/alembic/`). NATS used as the async coordination/messaging layer for sync workers and (per `ARCHITECTURE.md`) for "durable feedback subscriptions" using "threads and inbox leases."
- **Human interaction model**: Two connected but distinct mechanisms:
  1. `require_approval` policy action → `ApprovalRequest` created, notification fan-out to configured channels (mobile push, Slack, Mattermost, email, webhook), and either (a) **blocking**: the original tool-call HTTP connection stays open and polls until a decision is made or times out, or (b) **async**: Preloop returns immediately with a pending state + request ID, and the client later polls `get_approval_status`.
  2. `ask_user` / `request_approval` as an explicit tool the agent can call mid-task to ask a human a genuine question (not just "approve this action"). Implemented via `backend/preloop/services/ask_user_inband.py`. Critically, the docs/code state that answers delivered back through the agent's own "Agent Control" session channel **must never** be treated as the human's actual answer ("this would let an agent answer its own question") — real answers can only enter through the governed approval endpoints (console / mobile / public token link). This is a deliberate anti-self-approval design.
- **Retry / recovery**: `services/execution_recovery.py`, `services/execution_monitor.py`, `services/checkpoint_runtime.py`, `services/flow_continuation_adoption.py`/`flow_continuation.py` schema exist (file names only inspected — not read in depth); approval requests carry `expires_at` with default ~5 minutes and transition to `EXPIRED` on timeout, distinct from `CANCELLED`.
- **Permission / policy**: Enforced via `evaluate_policy()` returning a `PolicyDecision` (tuple/object of `action, approval_workflow_id, rule_description, rule_context`) which the MCP-endpoint handler acts on **before** looking up and invoking the real tool handler (`handler = server._tool_handlers.get(tool_name)` happens strictly after the policy/approval gate — confirmed from `dynamic_mcp_server.py`). A `DENY` short-circuits by returning a `TextContent` error to the agent — no exception, no downstream call. A `REQUIRE_APPROVAL` raises/awaits, and a timeout raises `TimeoutError` (caught → "Approval timeout: ..."), a decline raises `PermissionError` (caught → "Approval declined: ..." / "Tool execution cancelled"). Separately, model-gateway budget checks are enforced by `model_gateway_budget.py`'s `enforce_or_raise()`, called as a preflight before the model request is forwarded; violations raise an HTTP 403 with a specific message and an optional `Retry-After` header. An account/org-wide **kill switch** (`services/kill_switch.py`, `schemas/kill_switch.py`) can halt three independent scopes — `gateway`, `tools`, `flows` — with staged/selective re-enable, and any authenticated user can read kill-switch status (deliberately non-privileged read).
- **Audit**: `AuditLog` ORM model (`backend/preloop/models/models/audit_log.py`) — `account_id`, `user_id`, `action`, `resource_type`, `resource_id`, `status` ('success'/'denied'/'failure'), `ip_address`, `user_agent`, `details` (JSONB), `timestamp`, with a composite index `ix_audit_log_account_action_status_ts_ip` explicitly built for "CLI activity aggregations." **No immutability/append-only guarantee found in the model** (standard mutable SQLAlchemy ORM class — no soft-delete-only or trigger-enforced immutability observed). Separately, `ApprovalEvent`/`_record_event()`/`_log_approval_lifecycle_async()`/`_log_approval_notification_async()` in `approval_service.py` provide a parallel, approval-specific timeline (creation, decision, notification-delivery events) with correlation IDs and redacted tool arguments.
- **Credential handling**: Docs/architecture describe "secret custody" living inside the Model Gateway, which is stated to be "a central enforcement point for telemetry, budgets, session observability, and secret custody" — i.e., the design intent is that the agent/client never sees the real provider API key; Preloop mints/holds it and injects it server-side. `preloop agents discover` is also described as "minting managed credentials" when it rewires a local agent config. I did not read the actual credential-storage code (e.g. encryption-at-rest, KMS usage) — this remains **unconfirmed at the implementation level**, only confirmed as a stated design intent from architecture docs.
- **Provider/runtime coupling**: Model Gateway is explicitly "OpenAI- and Anthropic-compatible" (i.e., it speaks those two wire formats) and integrates with a broader model catalog (`ai_model_provider.py`, `litellm_routing.py`, `gemini_gateway.py`, `openai_gateway.py`, `deepseek_responses_reasoning.py` suggest LiteLLM-style multi-provider routing, not single-vendor lock-in). MCP-side, it explicitly targets any MCP-compatible client/server, not a single vendor.

(Primary code file paths cited above, all under `preloop/preloop@main`: `backend/preloop/services/dynamic_mcp_server.py`, `backend/preloop/services/policy_evaluator.py`, `backend/preloop/services/policy/schema.py`, `backend/preloop/services/policy/loader.py`, `backend/preloop/services/approval_service.py`, `backend/preloop/services/ask_user_inband.py`, `backend/preloop/services/model_gateway_budget.py`, `backend/preloop/services/kill_switch.py`, `backend/preloop/schemas/kill_switch.py`, `backend/preloop/models/models/approval_request.py`, `backend/preloop/models/models/audit_log.py`, `backend/preloop/models/models/event.py`, `backend/preloop/models/models/policy_snapshot.py`, `backend/preloop/models/models/policy_version.py`.)

# State Machine

Implemented (directly observed in code/docs, though several were read via a fetch-and-summarize tool rather than raw byte-for-byte diff — flagged where relevant):

- `ConditionAction` enum (`backend/preloop/services/policy/schema.py`): `ALLOW`, `DENY`, `REQUIRE_APPROVAL` (string-valued: `"allow"`, `"deny"`, `"require_approval"`). A separate `UnknownToolsPolicy` enum uses the same three values for the "tool not covered by any rule" default.
- `PolicyDecision` action space actually returned by `evaluate_policy()` (per docs and summarized source): `allow` / `deny` / `require_approval`, plus a documented **fourth** policy-authoring concept, `require_justification` (per `docs.preloop.ai/approvals/justification/` and the MCP concepts page) — implemented not as a fourth branch of the same execution-halting enum but as a **schema-injection mechanism**: Preloop dynamically adds a `justification` parameter (required or optional) to the tool's exposed schema, and the agent must fill it in as part of the same tool call. Missing justification in `required` mode causes rejection. This is a distinct enforcement path from `REQUIRE_APPROVAL`, layered on top of it rather than a sibling of `ConditionAction`.
- `ApprovalRequestStatus` (`backend/preloop/models/models/approval_request.py`, per fetch-and-summarize): `PENDING`, `APPROVED`, `DECLINED`, `EXPIRED`, `CANCELLED`.
- `KillSwitch` scope states (`backend/preloop/schemas/kill_switch.py`): per-scope halted/active state across three scopes (`gateway`, `tools`, `flows`), with staged/partial re-enable.
- `AuditLog.status`: `'success'`, `'denied'`, `'failure'` (string column, not a DB enum type per the summarized model).

Inferred (named in docs/architecture prose but not directly opened as source):

- Flow/issue-lifecycle states referenced in `ARCHITECTURE.md` prose ("structured readiness," "authorized implementation pickup," "independent merge/deployment acceptance audits," "fail-closed completion") suggest a richer state machine inside `services/issue_lifecycle.py` and `services/security_maintenance.py`, but the concrete enum values were not confirmed from source.
- `FlowExecution` likely has its own status enum (`schemas/flow_execution.py`, `models/models/` — file existence confirmed, contents not read).

If nothing else: no evidence was found of a single unified "Task/Run" style state machine across MCP tool calls, model-gateway calls, and Flows — these appear to be three semi-independent subsystems (MCP Firewall approval flow, Model Gateway budget-preflight, Flow/issue-lifecycle) each with its own state handling, rather than one canonical execution state machine.

# TACT Equivalent

- **Policy** → Preloop's YAML + CEL policy documents (`services/policy/schema.py`, `services/policy/loader.py`, `services/policy_evaluator.py`) are a genuine, close match to a TACT Policy concept: declarative rules, ordered/prioritized, evaluated deterministically (not by an LLM), producing a small closed decision type.
- **Approval / HumanInteraction** → `ApprovalRequest` / `ApprovalWorkflow` / `ApprovalEvent` map closely to TACT's Approval + HumanInteraction. The `ask_user` in-band mechanism (`ask_user_inband.py`) is a strong match for a genuine HumanInteraction-that-is-not-just-approval (asking a real question mid-task), including the explicit anti-self-approval boundary that TACT's "LLMs must never be trusted with Authorization decisions" principle would also want.
- **Permission** → Context/tool access rules (which tools an agent/API key/subject may call at all, `subject_governance.py`, `tool_approval_condition.py`, model `allowed_models` allowlisting) map to TACT's Permission concept, kept separate from the per-call Policy decision — consistent with TACT's "Context READ permission and Action WRITE permission are treated as separate permission types," though Preloop's split is closer to "static allow-list permission" vs. "dynamic per-call policy" than to TACT's read/write split specifically.
- **Audit** → `AuditLog` + `ApprovalEvent`/`_record_event()` map to TACT's Audit concept, though (see Risks) without a confirmed immutability guarantee, which TACT should not assume it can borrow as-is.
- **Execution** (halting a protected action before it happens) → the `DynamicMCPServer.handle_call_tool` gate — policy/approval resolved strictly before `_tool_handlers.get(tool_name)` is invoked — is a direct structural match for TACT's "a protected write must never execute before its Approval is granted."
- **Capability / Provider** → Preloop's MCP tool proxying + Model Gateway's multi-provider routing (OpenAI/Anthropic-compatible ingress, LiteLLM-style routing) is conceptually adjacent to TACT's Capability/Provider split, though Preloop's is scoped to "which model/tool traffic passes through," not TACT's broader Participant/Capability model of Work.
- **Work / Task / Run / Conversation** → **no genuine correspondence found.** Preloop has no first-class "Work" entity distinct from a tool call or a Flow execution; it does not model a Conversation/Work separation at all. Its "Flow" (issue-tracker-triggered automation) is the closest thing to a Task/Run-like execution record, but it is a narrower, ops/CI-flavored concept (SBOM checks, PR merge audits, security-advisory tracking), not a general Work-execution ledger. Do not force this mapping.
- **Artifact / Context** → Not directly mapped; Preloop's "evidence packs," "SBOM," and "Git bundle" artifacts (mentioned in `ARCHITECTURE.md`) are domain-specific (software supply-chain compliance) rather than a general Artifact concept like TACT's.

# Reusable Schema

- **Policy decision shape** — `PolicyDecision` as `(action, approval_workflow_id, rule_description, rule_context)` where `action ∈ {allow, deny, require_approval}` plus the separate justification-injection mechanism — is a good reference shape for TACT's own Policy decision type. ADAPT, not copy: TACT's 4-outcome ask (ALLOW / REQUIRE_APPROVAL / REQUIRE_INPUT / DENY) does not line up 1:1 — Preloop's `require_justification` is agent-self-reported metadata attached to the same call, not a genuine "pause and get real external input" primitive the way TACT's REQUIRE_INPUT / `ask_user` a real question implies. TACT's REQUIRE_INPUT maps better to Preloop's separate `ask_user` in-band mechanism than to `require_justification`.
- **ApprovalRequestStatus enum** (`PENDING / APPROVED / DECLINED / EXPIRED / CANCELLED`) — directly adaptable shape for a TACT Approval status enum; distinguishing `DECLINED` (explicit human no) from `EXPIRED` (timeout, no decision) from `CANCELLED` (withdrawn) is a useful distinction TACT should consider keeping separate rather than collapsing into a generic "rejected."
- **KillSwitch scope model** (independent halt flags across `gateway` / `tools` / `flows`, staged re-enable, non-privileged read) — a reasonable reference shape if TACT ever wants an emergency-stop primitive scoped per execution surface rather than global.
- **AuditLog columns** (`action`, `resource_type`, `resource_id`, `status`, `details` JSONB, indexed by account/user/action/resource/status/timestamp) — a reasonable reference shape, but not verified as append-only/immutable, so treat as a starting point only, not a finished design.

# Reusable Pattern

- **Pre-execution policy gate on tool calls, enforced at the execution layer (not the LLM), with fail-closed on evaluation error** — this is the single most transferable pattern: policy resolution happens strictly before the downstream tool handler is invoked, and if policy evaluation itself throws, the system defaults to `require_approval` rather than `allow`. Directly aligned with TACT's own stated principle that Policy/Permission/Approval must be enforced deterministically at the Execution Layer.
- **First-match, priority-ordered rule evaluation with an explicit default** (default `allow` when no rule matches, in Preloop's case) — simple, auditable rule-resolution semantics worth reusing conceptually. Note TACT would need to decide its own default polarity (Preloop defaults open/`allow`; a more conservative TACT default might be closer to `require_approval` or `deny` depending on the class of action).
- **Anti-self-approval boundary**: an in-band notice channel to the agent's own session is explicitly documented as informational-only — real answers/approvals must come back through a separate, governed channel, never through the same connection the agent controls. This is a directly reusable safety pattern for any TACT `ask_user`/REQUIRE_INPUT design, and reinforces TACT's own "LLMs must never be trusted with Authorization decisions" rule at the protocol level, not just the prompt level.
- **Justification-as-schema-injection**: dynamically adding a required/optional explanation field to a tool's own call schema, rather than a separate approval step, for lower-risk-but-still-sensitive actions. A cheap middle tier between plain ALLOW and full REQUIRE_APPROVAL, worth considering as a lightweight TACT variant — but see Risks: this is agent-self-reported text, not verified human input, so it should not be treated as an Approval-equivalent for protected writes.
- **Scoped kill switch with staged recovery** — halting by traffic class (`gateway`/`tools`/`flows`) rather than one global on/off switch, so an operator can, e.g., halt tool execution while still allowing model calls to complete gracefully.

# Reusable UX

- **Blocking vs. async approval as a client-chosen mode**: the same policy outcome (`require_approval`) supports either holding the connection open (simple client experience, tolerates latency) or returning a pending state + request ID for polling (`get_approval_status`) — a reasonable UX pattern for TACT's own human-approval waiting states, letting the calling surface pick which mode fits it rather than TACT dictating one.
- **Multi-channel approval notification with a truncated reasoning summary** (agent's `agent_reasoning` shown truncated to 500 chars in approval notifications across email/Slack/mobile) is a reasonable reference for how to surface "why is this waiting for me" concisely to a human approver.
- Beyond this, the actual Console UI (Lit/Vite/TypeScript/Shoelace) was not inspected visually (no screenshots reviewed, `tmp-reference*.png` in this repo were explicitly out of scope and not used) — no further UX detail can be confirmed beyond what the docs/code prose describes above.

# Risks

- **License**: Core repo is Apache-2.0 (permissive, low risk for REFERENCE_ONLY / pattern-borrowing use). Unconfirmed risk: whether "Enterprise" behavior (quorum approvals, AI-driven approvals, RBAC) is fully open-source in this repo or partly gated/proprietary — the `ApprovalRequest` schema fields for both already exist in the Apache-2.0 repo, so at minimum the *schema* is open, but *behavior/activation* could be commercially licensed. Do not assume the full approval feature set described in marketing pages is Apache-2.0 in practice without checking the actual gating code.
- **Security**: `decided_by_ai` / `ai_model` / `ai_confidence` / `auto_approved_reason` fields exist on `ApprovalRequest`, meaning Preloop's own architecture supports **AI models making approval decisions** in at least some configuration/tier. This directly conflicts with TACT's hard rule that "LLMs must never be trusted with Authorization decisions." Do not import this capability or its schema fields as-is into TACT's Approval model without stripping/rejecting the AI-decides path.
- **Provider lock-in**: Low — explicitly multi-provider (OpenAI/Anthropic-compatible gateway, LiteLLM-style routing, generic MCP support).
- **Runtime lock-in**: Moderate — Preloop is architected as a standalone Python/FastAPI service with its own Postgres+NATS deployment (Docker Compose/Kubernetes/Helm), not a library. Adopting it as a real dependency (rather than a design reference) would mean running a second service alongside TACT's Next.js/Supabase stack — out of scope for this investigation, and inconsistent with "Build less, Orchestrate more" only if TACT actually wants to delegate MCP-gating wholesale rather than borrow the pattern.
- **Architecture mismatch**: Preloop has no Work/Conversation separation and no general Task→N-Runs execution ledger; its unit of governance is a single tool call or model call, not a multi-step Work item. Mapping TACT's Work/Task/Run concepts onto Preloop would be force-fitting — flagged explicitly, not done, in the TACT Equivalent section above.
- **Agent-centric bias**: Yes — Preloop's entire vocabulary (agents, tool calls, MCP clients) is agent-centric, whereas TACT's center is Work with Agent as one of several Participant types. Borrow the *policy-gate* pattern, not the agent-centric framing.
- **Overengineering**: Preloop's scope (issue-tracker sync, SBOM/compliance evidence packs, model-pricing catalogs, multi-channel notification delivery, quorum voting, Flows/CI automation) is much broader than what TACT needs from this investigation (policy/approval/execution gating). Adopting more than the policy-gate + approval-state-machine + anti-self-approval pattern risks importing unrelated complexity.
- **Scaling concern**: Not assessed — no load/perf data found in the repo or docs during this check.
- **Persistence mismatch**: Preloop uses Postgres+PGVector+NATS as its own store; TACT's rule is that Supabase is the single source of truth for TACT-owned state. Any adopted schema would need to be re-expressed as Supabase tables/RLS, not imported as-is.
- **Multi-tenant concern**: Preloop's models are explicitly multi-tenant (`account_id` on nearly everything, cascade-delete FKs) — directionally compatible with typical SaaS multi-tenancy, but its specific tenancy model (Account → Organization → Team → User) was not compared in detail against TACT's own tenancy model in this investigation.
- **Secret handling**: Stated design intent ("secret custody" in the Model Gateway, "minting managed credentials") was found only in architecture prose, not verified against actual credential-storage implementation (encryption at rest, KMS/HSM use, rotation). Do not cite this as a confirmed secure pattern — mark as **Inferred**, not Implemented, until the actual credential storage code is read.

# Recommendation

## Adopt
- The **pre-execution, execution-layer policy gate** shape: resolve Policy → (ALLOW / REQUIRE_APPROVAL / REQUIRE_INPUT / DENY) strictly before any protected write executes, with a deterministic, non-LLM evaluator, and fail-closed behavior if the evaluator itself errors.
- The **anti-self-approval boundary** as an explicit, protocol-level rule for any TACT `ask_user`/REQUIRE_INPUT design: a response arriving back over the same channel the Agent/LLM controls must never be accepted as the human's actual answer.
- A **richer Approval status enum** distinguishing declined vs. expired vs. cancelled (not just "rejected"), if TACT's current Approval status enum does not already make this distinction.

## Do Not Adopt
- Any notion of AI/LLM-decided approvals (`decided_by_ai`) — directly conflicts with TACT's core Authorization principle.
- Preloop's own runtime/service (Python/FastAPI/Postgres/NATS) as an actual dependency — TACT should only borrow the *pattern*, not run Preloop as infrastructure, absent a much larger, explicitly-approved architecture decision.
- Preloop's broader scope (issue-tracker sync, Flows/CI automation, SBOM/compliance evidence, quorum/RBAC/multi-user features) — out of scope for TACT's Policy/Approval/Execution layer today; importing it would be overengineering relative to the stated need.

## Why
Preloop is a real, actively-maintained, Apache-2.0 project that already solved — in a genuinely comparable governance domain (gating AI-agent tool calls before they execute, with human approval and audit) — several of the exact design questions TACT's own CLAUDE.md already commits to: policy/permission enforced deterministically at the execution layer, not via LLM judgment; a protected write must never execute before its Approval is granted. Preloop's concrete implementation (evaluate-before-invoke ordering, fail-closed evaluator, distinct approval states, and especially the anti-self-approval channel separation) is useful **evidence that this class of design works in practice**, and gives TACT specific enum/shape vocabulary to compare its own Policy/Approval types against — without needing to adopt Preloop's code, stack, or scope.
